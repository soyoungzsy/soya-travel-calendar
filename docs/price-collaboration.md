更新时间：2026-10-29。此文不含密钥、用户资料或真实用户行为明细。

## 从自己的电脑参与

项目仓库是 <https://github.com/soyoungzsy/soya-travel-calendar>，公开仓库。推荐 Fork 后提交 PR，不需要使用 SOYA 的电脑，也不需要 SOYA 的 GitHub、腾讯云或 ChatGPT 登录。

1. 用自己的 GitHub 账号 Fork 仓库，然后把自己的 Fork 克隆到电脑。
2. 安装 Node.js 22.12 或更新版本，在目录执行 `npm ci`。先读 `AGENTS.md` 和 `CONTRIBUTING.md`。
3. 本轮最新迭代位于原仓库的 [`feat/module-analytics` 分支](https://github.com/soyoungzsy/soya-travel-calendar/tree/feat/module-analytics)，尚未合并到 `main`。先把原仓库设为 `upstream`，获取这个分支，再从它新建自己的 `feat/live-travel-compare` 分支。可将本说明交给自己的开发助手完成；不要直接从旧版主分支覆盖本轮改动。执行 `npm run dev` 可检查前端，或 `npm run build` 后执行 `npm start` 检查现有 Node 适配器。
4. 修改自己的分支，先 `npm run build`，再 `npm test`，提交到自己的 Fork，并向原仓库提出 PR。说明实际查询结果、测试、尚未验证的字段和部署依赖。
5. SOYA 审阅改动及预览后决定合并，由项目所有者配置正式凭据并发布。GitHub 提交、PR 合并、网站发布是三个不同步骤。

GitHub 官方流程：<https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-a-project>。

如果长期合作，也可以由 SOYA 邀请朋友成为仓库协作者，在同一仓库的独立分支工作；当前采用 Fork 即可开始，不需要先扩大权限。`127.0.0.1` 是各自电脑的本机地址，不能把 SOYA 的本机样板链接当作共享线上预览。

- 2026-10-24 通过原版 FlyAI 官方 CLI 完成过一条国内单程航班和一条酒店真实查询。能返回具体展示金额，但不证明国际往返、酒店全程总价、税费和公开网站调用已验通。
- [草稿 PR #11](https://github.com/soyoungzsy/soya-travel-calendar/pull/11) 修复货币符号金额、营销航司字段及官方预订链接识别。本轮读取时仍是 draft、open、未合并。请先检查它，避免重复修复或覆盖。
- 贝加尔湖本地内容样板中的几组机酒数字是假设值，用于检验计算，不是库存或历史行情。它不在正式报价流程里。

## 为什么还没有在网页查通

1. `FLYAI_WEBSITE_ENABLED` 默认保持关闭，直到正式调用方式验收完成。仅填入 Key 不代表接通。
2. 当前适配器假定能通过 `https://flyai.open.fliggy.com/mcp` 使用 Bearer 授权初始化 MCP。本人 CLI 查询成功，没有证明此直接 HTTP 方式所需的鉴权、协议和参数都一致。要依据官方支持的 SDK／HTTP／MCP 文档验证，不能复制 CLI 的内部体验凭据、签名常量或伪造客户端环境。
3. 当前 Node 服务只向 Worker 提供 `ASSETS`，没有自动接入报价 Key 或额度数据库；Vite 预览仅代理报价状态接口，没有直接代理搜索 POST。把 Key 放进本机环境后直接运行前端，不会使报价自动可用。需要明确实现并测试服务端适配。
4. 现有查询按单程分别核价，酒店返回的单位、人数、房型与税费没有全部确认。不能直接生成“完整往返＋酒店全程”的可比较总价。
5. 地点显示名不一定是酒店搜索城市。例如贝加尔湖需按伊尔库茨克、利斯特维扬卡或胡日尔的实际住宿段查询，不能搜索湖名后把一个城市的报价套到整条线路。本轮源码已修正湖区默认城镇，但仍不代表供应商已匹配到对应酒店。
6. 没有获准保存并连续采集的历史报价库，所以不能称已经有“近30天最低”或“比平时便宜多少”。

## 第一个应交付的结果

先打通一条指定出发地与目的地、有效未来日期的真实查询，从网页请求到服务端再到供应商，最后返回网页。接着验证酒店、国际目的地及无结果／错误分支。暂时无需大规模后台扫描，也无需购买服务器。

开发者可以用自己的正式测试账号和服务端凭据验证。正式网站是否允许公共访问者使用个人免费授权、调用限额及报价保存范围，以供应商条款和控制台为准。生产凭据由所有者放在服务端，不放前端、Git、截图或交接文档。不要为改价格提供证件、私人地点或用户行为明细。

## 标准化响应必须说清楚

| 类型 | 最少需要的已确认信息 |
| --- | --- |
| 航班 | 实际机场、出发到达时间与时区、单程／完整往返／分开购票组合、人数与舱位、币种、金额按人还是整单、必付税费、行李／退改条件、来源与查询时间 |
| 酒店 | 具体酒店、入住离店、入住人数、房间数、房型、餐食与取消条件、币种、每晚还是整段住宿总价、必付税费、来源与查询时间 |
| 价格完整性 | 未返回的字段保留未知。只有满足比较条件且金额完整时才进入机酒合计；否则作为带来源的商品参考或平台查价入口 |

## 比较与预算共用同一份明细

- 候选目的地之间比较同一份假期、人数、舱位及住宿需求下的机酒合计，也展示实际路途与可用游览时间。不能把最低机票当成最低旅行花费。
- 同一个目的地是否划算，需要同机场、日期和商品条件的参考样本。相邻日期是另一种比较，改变日期后不能沿用原日期的历史基准。
- 每人机酒合计 = 每人交通报价 + 全部房间全程住宿总价 ÷ 出行人数。
- 全程预算原来已有 `flight`、`stay`、`food`、`local`、`activities` 分项。取得完整交通和住宿报价后，替换对应估算，再加其他估算；不要在原总预算上再加一次机酒。
- 酒店“每晚起价”不能直接乘晚数。不同城镇的住宿必须按各段真实入住日期合计。过夜交通日不一定需要目的地酒店。
- 不同币种只有在汇率来源和时间明确时才换算，保留原币金额。失效报价不能标为当前可订。

## 接口与代码边界

先固定供应商响应标准化结构，再写比较逻辑，最后接 UI。建议把标准化报价和预算替换放进独立模块，减少与国内周末游、统计和内容编辑的冲突。不要未经协议核对，给旧 MCP 请求随意添加房间数等供应商不支持的参数。

保留同源限制、请求大小限制、全站调用额度与失败提示。离开 Sites 的环境，需要自己的数据库和可信登录校验，不能直接信任浏览器提交的 Sites 所有者身份头。

## PR 验收清单

- 指定日期和机场的真实航班能经网页往返获得结果；结果不是本地假数据。
- 酒店结果能够确认按房晚还是整段住宿、房间人数与必付费。
- 国内和国际至少各核对一条真实路线，国际覆盖不足时如实说明。
- 去返程日期、中转、跨日到达与住宿段正确，不拿“贝加尔湖”作为所有住宿的城市。
- 缺字段、无结果、鉴权失败、额度耗尽及供应商错误不填虚假金额。
- 改日期、人数、房间或方案后，旧结果不会继续作为新条件报价显示。
- 预算替换无重复计费，一日游没有住宿费；历史参照不足时不显示价差百分比。
- 附来源与查询时间、脱敏后的必要响应字段、构建和测试结果；无密钥或个人信息。

最终发布由所有者处理。PR 讨论可异步进行，SOYA 只需要看预览和验收结果，不需要两个人同时在线操作一台电脑。
